# US — ONBOARDING ADJUSTMENT
## Remove SMS OTP from V1

We have completed the onboarding implementation:

- USN
- Optional student email
- Profile creation
- Photo upload
- RLS policies
- Database migrations
- Supabase Storage
- Build passes
- Lint is clean

The current implementation also contains phone OTP through Supabase Auth.

We are intentionally removing SMS/phone OTP from V1.

Do NOT rebuild the onboarding system from scratch.

Modify the existing implementation cleanly.

==================================================
V1 VERIFICATION MODEL
==================================================

For V1, use:

USN
+
optional student email

Phone/SMS authentication is OUT OF SCOPE for now.

The reason is to keep the initial product:

- faster to launch
- simpler
- lower operational cost
- easier to test with campus users

Phone verification can be added later without redesigning the public profile model.

==================================================
AUTHENTICATION
==================================================

Remove the phone OTP flow from the onboarding UX.

Do not ask the user for a phone number during onboarding.

Do not send SMS.

Do not create any dependency on an SMS provider.

Keep Supabase Auth if it is already being used for session/account management, but use an authentication method that does not require SMS.

If the current authentication implementation requires phone authentication, refactor it so the onboarding architecture does not depend on phone verification.

Do not invent a new authentication provider.

==================================================
DATABASE
==================================================

Review the existing migrations.

If verification_records currently contains phone-related fields such as:

phone_verified

remove them if they are not needed by the current V1 architecture.

Do not blindly modify an already-applied migration.

Create a new migration for schema changes if necessary.

The final conceptual verification model should be:

verification_records

- id
- user_id
- usn
- email (nullable)
- email_verified (if applicable)
- verification_status
- created_at
- updated_at

The exact schema may differ if the existing implementation has a cleaner design.

Do not store unnecessary personal information.

==================================================
USN
==================================================

USN remains required.

The flow should be:

Landing
   ↓
Enter the campus
   ↓
USN
   ↓
Optional student email
   ↓
Profile
   ↓
Photos
   ↓
Discover

The USN remains private.

It must never appear in:

- profile cards
- discovery responses
- public API responses
- URLs
- chat
- client-visible profile identifiers

USN validation remains isolated in:

lib/verification/usn.ts

Do not invent the final college-specific regex.

==================================================
OPTIONAL EMAIL
==================================================

Student email remains optional.

Do not require it.

If supplied, store it separately from the public profile.

Do not expose it to other students.

==================================================
PROFILE
==================================================

Keep the existing profile implementation:

Required:

- nickname
- age
- year
- branch
- minimum one photo

Optional:

- bio
- interests

Maximum:

6 photos

==================================================
SECURITY
==================================================

Review RLS after removing phone authentication.

Ensure that removing phone verification does NOT make any table more permissive.

Users must not be able to access another user's:

- USN
- email
- verification record

Keep all sensitive verification information isolated.

Never expose Supabase service-role credentials.

==================================================
UX
==================================================

The onboarding should now feel shorter.

Do not leave an empty "phone verification" screen.

Do not mention SMS anywhere in the V1 onboarding.

Transitions should remain smooth and consistent with the existing US design.

==================================================
TESTING
==================================================

Verify:

- fresh onboarding
- returning user
- incomplete onboarding
- USN validation
- duplicate USN
- optional email skipped
- optional email supplied
- profile creation
- photo upload
- RLS
- authenticated session
- unauthorized access attempts

IMPORTANT
==================================================

Do NOT build:

- swipe

- Three.js
- phone/SMS verification

Those come later.
