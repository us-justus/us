==================================================
STEP 1 — PHONE
==================================================

Create a phone authentication screen.

The user enters:

Phone number

Use Supabase Auth for authentication.

IMPORTANT:

Do not expose phone numbers anywhere in the public profile.

The phone number is verification/authentication data only.

Use proper validation.

The UI should clearly communicate why the phone number is required without sounding corporate.

Example conceptual copy:

"Let's make sure you're real."

"Your number stays private."

Do not blindly copy this wording if it doesn't fit the existing design.


==================================================
OTP
==================================================

Implement the architecture for Supabase phone OTP authentication.

The flow should support:

Enter phone
   ↓
Request OTP
   ↓
Enter OTP
   ↓
Verify OTP
   ↓
Authenticated session


Do not build fake OTP verification.

Use the actual Supabase authentication flow.

Handle:

- invalid phone number
- incorrect OTP
- expired OTP
- resend OTP
- excessive resend attempts
- loading states
- network failures


IMPORTANT:

Do not claim OTP is free.

The application should be structured around Supabase Auth, but actual SMS delivery may incur provider costs depending on configuration.


==================================================
STEP 2 — USN
==================================================

After successful authentication, request the student's USN.

The USN is PRIVATE verification information.

It must never appear in:

- profile cards
- public APIs
- URLs
- chat
- discovery responses
- frontend state after verification if it is no longer required


Create:

lib/verification/usn.ts


Create a function with this conceptual API:

validateUSN(usn: string): boolean


IMPORTANT:

DO NOT invent the final college-specific regex.

For now create a clearly isolated placeholder validator.

Example conceptual structure:

export function validateUSN(usn: string): boolean {
    // TODO:
    // Replace with the final college-specific USN regex.
    return false;
}

The exact regex will be added later.

Normalize input safely:

- trim whitespace
- uppercase where appropriate
- reject obviously invalid input
- never log the USN


==================================================
VERIFICATION RECORD
==================================================

Create a private verification record associated with the authenticated user.

Conceptually:

verification_records

id
user_id
usn
phone_verified
email_verified
verification_status
created_at
updated_at


Do NOT expose this table directly to normal client queries.

The USN should be protected by Row Level Security.

Prefer server-side verification operations where appropriate.

Do not allow users to query other users' verification records.


==================================================
USN UNIQUENESS
==================================================

A USN should only be associated with one account.

Add a database uniqueness constraint.

If a user attempts to register a USN that already exists:

Show a generic message such as:

"This USN is already associated with an account."

Do not reveal who owns it.


==================================================
OPTIONAL EMAIL
==================================================

Allow the student to optionally provide a student email.

Email should NOT be required in V1.

The interface should clearly indicate:

Optional

Do not block onboarding if the user skips it.

Store it separately from public profile data.

Do not display it publicly.

==================================================

- Age

- Branch
- At least one profile photo

Optional:

- Interests

The public profile should contain only information appropriate for discovery.


==================================================
AGE
==================================================

The V1 service is intended for adults.

Require the user to confirm that they meet the minimum legal age requirement before creating a dating profile.

Do not expose date of birth publicly.

Prefer storing only the minimum age-related information required for the product.

Do not collect unnecessary personal information.

==================================================
ROW LEVEL SECURITY
==================================================

Enable RLS on all application tables.

A normal authenticated user should be able to:

- create their own profile
- update their own profile
- read their own profile
- manage their own photos
- manage their own verification record only where required

A user must NOT be able to:

- read another user's USN
- read another user's phone
- read another user's email
- modify another user's profile
- modify another user's photos
- access arbitrary storage objects


Discovery access will be implemented separately.

Do not create overly permissive policies such as:

authenticated users can select everything.
