# US — IMPLEMENTATION PROMPT 03
## Discover & Premium Swipe Engine

You are continuing development of "us", a private campus-only dating web application.

The foundation and onboarding are already implemented.

Current V1:

- US branding
- Landing page
- Supabase foundation
- USN verification
- Optional student email
- Profile creation
- Profile photos
- RLS
- Storage
- Database migrations
- Onboarding flow
- No SMS/phone OTP in V1

The next task is to build the DISCOVER experience.

This is the most important interaction in the product.

The swipe experience must feel exceptionally smooth, deliberate, responsive, and premium.

It must NOT feel like a quickly assembled swipe-card demo.

==================================================

On mobile, the primary screen should feel almost entirely dedicated to discovery.

Conceptually:

                 us

==================================================
PROFILE CARD
==================================================

Each card should display:

- primary profile photo
- nickname
- age
- year
- branch
- optional bio/interests

The card should support multiple photos.

Users should be able to move between photos naturally.

Do not make the card feel like a form or information panel.

Photography should be the dominant visual element.


==================================================
CARD STACK
==================================================

Implement a small card stack.

At minimum:

Current card
Next card
One additional preloaded card where useful

The next card should subtly exist underneath the current card.

When the current card leaves:

Next card should smoothly become active.

Avoid rendering an unnecessarily large number of profile cards.


==================================================
SWIPE PHYSICS
==================================================

This is the most important section.

Use Motion for React for gesture and animation handling.

Do NOT implement the swipe system using:

- setInterval
- manually controlled CSS animations
- excessive React state updates during drag
- Three.js
- polling

The card should respond directly to the user's gesture.

During horizontal dragging:

translationX follows the pointer/finger.

Rotation should be proportional to horizontal displacement.

Example conceptual relationship:

rotation = translationX * small_factor

Keep rotation subtle.

The card should feel like a physical object being moved rather than a DOM element being teleported.


==================================================
VELOCITY
==================================================

Swipe decisions should account for both:

distance
and
velocity

A fast flick should be able to dismiss the card even if the total distance is relatively small.

A slow drag should require crossing a reasonable threshold.

Do not use only:

if x > threshold → like

Use gesture velocity as part of the decision.


==================================================
SWIPE THRESHOLD
==================================================

Create a centralized swipe configuration.

For example:

SWIPE_THRESHOLD
SWIPE_VELOCITY_THRESHOLD
MAX_ROTATION
EXIT_DISTANCE
SPRING_CONFIG

Do not scatter magic numbers throughout components.

Tune these values after testing on an actual mobile viewport.


==================================================
LIKE / PASS
==================================================

Horizontal direction:

RIGHT → LIKE
LEFT → PASS

Buttons should also be available.

The buttons are a secondary interaction.

Primary interaction is gesture-based.


==================================================
DIRECTIONAL FEEDBACK
==================================================

While dragging:

RIGHT:

show a subtle Like indicator.

LEFT:

show a subtle Pass indicator.

The indicator should respond continuously to the drag amount.

Example conceptual behavior:

small drag:
almost invisible

medium drag:
visible

large drag:
clearly visible

Do NOT suddenly pop the indicator into existence.


==================================================
CARD ROTATION
==================================================

Rotation should feel natural.

The card should rotate around a visually believable anchor point.

Avoid excessive rotation.

It should never look like:

"rotate: 30deg"

Use a restrained range.

The exact values should be tuned by feel.


==================================================
NEXT CARD
==================================================

The next card should be slightly scaled down and/or offset behind the active card.

As the current card moves away:

the next card should subtly scale toward its active position.

Example conceptual behavior:

next card:
scale 0.96

during dismissal:
scale → 1

Do not over-animate it.

The user should subconsciously perceive continuity.


==================================================
RELEASE / SPRING BACK
==================================================

If the swipe does not meet the dismissal criteria:

the card should spring back to its original position.

It should NOT:

- snap
- teleport
- slowly drift
- use a linear animation

Use spring physics.

The spring should feel:

- quick
- natural
- slightly tactile


==================================================
DISMISSAL
==================================================

When a card is dismissed:

1. Determine LIKE or PASS.
2. Persist the action.
3. Animate the card beyond the viewport.
4. Promote the next card.
5. Prepare another card.

Do not wait for a network request before allowing the animation to begin.

The UI should feel instantaneous.

Persist the action asynchronously where safe.

Handle failures without making the interface feel broken.


==================================================
DATABASE
==================================================

Create the initial interaction tables.

likes:

- id
- from_user_id
- to_user_id
- created_at

passes:

- id
- from_user_id
- to_user_id
- created_at

Use UUIDs.

Add appropriate unique constraints.

A user should not be able to create duplicate likes for the same target.

A user should not be able to create duplicate passes for the same target.


==================================================
MATCH CREATION
==================================================

For V1, implement the matching logic.

When:

A likes B

and B has already liked A

create a match.

matches:

- id
- user_a_id
- user_b_id
- created_at

Prevent duplicate matches with a database constraint/design that normalizes the pair.

Do NOT trust the client to decide whether a match exists.

The server/database must determine this.


==================================================
IMPORTANT — UI FIRST
==================================================

The animation must not depend on a slow database response.

Sequence:

USER SWIPES
     ↓
LOCAL UI RESPONSE
     ↓
CARD ANIMATION
     ↓
ACTION PERSISTED
     ↓
MATCH RESULT
     ↓
MATCH UI IF NECESSARY


==================================================
MATCH MOMENT
==================================================

When a Like creates a mutual match, show the US match experience.

Primary copy:

"it's a match."

Secondary:

"you both liked each other."

Keep the animation elegant.

Do NOT use:

- confetti
- explosions
- loud sounds
- huge hearts
- excessive particles

Think:

quietly exciting.

The moment should feel special without becoming cheesy.


==================================================
MATCH UI
==================================================

Create a polished match transition.

Possible sequence:

card exits
    ↓
subtle transition
    ↓
match state
    ↓
"it's a match."
    ↓
"you both liked each other."
    ↓
actions:
"say hi"
"keep discovering"

Do not force the user into chat immediately unless the UX feels appropriate.

Keep the interaction reversible.


==================================================
PHOTO NAVIGATION
==================================================

If a profile has multiple photos:

Allow intuitive navigation between them.

On mobile:

tapping the left/right side of the photo can move between images.

Do not make this interfere with horizontal swipe gestures.

Use clear but subtle photo progress indicators.

Example:

● ○ ○ ○


==================================================
IMAGE PERFORMANCE
==================================================

Image performance is critical.

Use:

- Next.js image optimization where appropriate
- responsive image sizing
- appropriate object-fit
- lazy loading for future cards
- preload the current and next profile images
- avoid loading every profile's full-resolution photos

Do not sacrifice visual quality unnecessarily.


==================================================
DISCOVERY DATA
==================================================

Create a server-side discovery query.

Only return profiles that are eligible.

Exclude:

- current user
- users already liked
- users already passed
- blocked users
- users who blocked the current user
- inactive profiles
- incomplete profiles

Do not return:

- USN
- email
- phone
- verification data


==================================================
PRIVACY
==================================================

The discovery API/query must only expose public profile fields.

Conceptually:

nickname
age
year
branch
bio
interests
photos

Never:

USN
phone
email
verification records


==================================================
BLOCKING
==================================================

The discovery query should already be structured so blocked users can be excluded.

If a block table does not yet exist, create it.

blocks:

- id
- blocker_id
- blocked_id
- created_at

Unique:

blocker_id + blocked_id


==================================================
LOADING
==================================================

Do NOT show a generic full-screen spinner every time another card loads.

The initial loading state can be minimal and branded.

After the first cards are loaded:

the user should almost never perceive a loading transition between cards.

Prefetch the next profile(s).


==================================================
EMPTY STATE
==================================================

When there are no more profiles:

do not show:

"No data found."

Instead create an intentional US state.

Conceptually:

"that's everyone for now."

"check back later."

Use the existing visual language.

Do not invent excessive copy.


==================================================
ERROR HANDLING
==================================================

If a swipe persistence request fails:

Do not reset the entire discovery stack.

Handle the failure gracefully.

Consider retrying where appropriate.

Do not allow an accidental duplicate action.

Show a subtle user-facing error only when necessary.


==================================================
ACCESSIBILITY
==================================================

Although gestures are primary, the experience must remain usable without gestures.

Provide:

- Like button
- Pass button
- keyboard support on desktop
- visible focus states
- accessible labels
- reduced-motion support

Example accessible labels:

"Like Maya"

"Pass Maya"


==================================================
MOBILE
==================================================

Mobile is the primary platform.

Test:

- 360px wide
- 390px wide
- 430px wide

The swipe area must not accidentally trigger browser scrolling.

Use appropriate touch-action behavior.

Do not prevent all browser gestures unnecessarily.


==================================================
DESKTOP
==================================================

Desktop should still feel intentional.

Do not simply stretch the mobile card to enormous dimensions.

Center the discovery experience.

Maintain a sensible maximum card width.

Mouse dragging should feel as natural as touch dragging.


==================================================
PERFORMANCE
==================================================

Target:

60 FPS during dragging.

During active dragging:

avoid unnecessary React re-renders.

Use Motion's motion values / transforms where appropriate.

Do not calculate expensive layout operations on every pointer movement.

Do not perform network requests during every movement event.

server data
from

Gesture state should not cause unnecessary database/state updates.

==================================================
QUALITY BAR
==================================================

Before finishing, manually inspect the swipe experience.

Ask:

Does the card follow the finger immediately?

Does it feel physically attached to the gesture?

Does a fast flick feel satisfying?

Does a slow drag feel controlled?

Does the spring-back feel natural?

Does the next card appear smoothly?

Does the card exit without stuttering?

Does the UI remain responsive while the network request happens?

Does it feel good on an actual phone?

If any answer is no, tune the interaction before considering the task complete.
