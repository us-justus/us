We are continuing development of the `us` campus-only dating app.

CURRENT STATE
- Next.js 16.3.5 + App Router + TypeScript
- Tailwind CSS
- Supabase Auth/Postgres/Storage/Realtime
- Anonymous Supabase auth currently works
- Onboarding works end-to-end:
  /onboarding
  /onboarding/usn
  /onboarding/email
  /onboarding/profile
  /onboarding/photos
- Profile creation already works during onboarding.
- Profile photos can already be uploaded/deleted.
- Discover/swiping is already implemented.
- `/profile` does NOT currently exist.
- Profile editing is the next feature to build.
- We are testing on a real phone over LAN, so the UI must be genuinely mobile-first.

PRODUCT / PRIVACY RULES
The app is called `us`, tagline `just us.`

Public profile information:
- nickname
- age
- year
- branch
- photos
- optional bio
- optional interests

Private information:
- USN
- email
- Supabase auth/user ID
- verification metadata

Never expose USN, email, auth IDs, or verification records in public profile queries/UI.

GOAL
Build a polished `/profile` page that lets the authenticated user view and edit their own profile.

BEFORE CODING
1. Inspect the existing database schema/migrations.
2. Inspect the existing profile onboarding components and API/server actions.
3. Inspect existing Supabase RLS policies.
4. Reuse existing types, validation, queries, storage helpers, and UI primitives wherever possible.
5. Do NOT duplicate business logic unnecessarily.
6. Do NOT change the database schema unless absolutely necessary.

PROFILE PAGE REQUIREMENTS

Create:

`/profile`

It should show:

- profile photos
- nickname
- age
- year
- branch
- bio
- interests

Provide an obvious `Edit profile` action.

EDITING

The user must be able to edit:

- nickname
- age
- year
- branch
- bio
- interests

For interests, use the existing data model if one already exists. If the current schema stores interests differently, follow the existing schema rather than inventing a new representation.

Validation:
- Reuse onboarding validation where possible.
- Keep the same constraints between onboarding and editing.
- Never allow a user to edit their USN.
- Never allow a user to edit verification metadata.
- Never allow editing another user's profile through this UI/API.

PHOTOS

Build a mobile-friendly photo management section.

Required:
- view current photos
- add/upload photos
- delete photos
- reorder photos

The database already has `display_order`, so use that rather than inventing a new ordering mechanism.

The first photo should be clearly treated as the primary profile photo.

Photo operations must respect the existing Supabase Storage + RLS/security model.

Do not expose storage objects or private metadata unnecessarily.

UX

This is a dating app, so do NOT make this look like a generic admin dashboard.

Design direction:
- minimal
- romantic
- polished
- subtle
- premium
- Gen-Z but restrained
- typography-led
- plenty of whitespace
- smooth interactions
- mobile-first

Avoid:
- dashboard cards everywhere
- excessive gradients
- excessive glassmorphism
- unnecessary icons
- huge headings
- generic SaaS styling
- unnecessary animations

Mobile requirements:
- optimized for ~360–430px wide phones
- comfortable touch targets
- sticky/fixed save action only if it genuinely improves UX
- respect safe areas
- avoid horizontal overflow
- keyboard should not cover important controls
- photo management should work comfortably with touch
- test at both narrow and larger mobile widths

EDIT FLOW

Prefer a simple experience such as:

Profile
  ↓
Edit profile
  ↓
Edit fields
  ↓
Save changes
  ↓
Return to profile

For photo management, make the interaction obvious without adding unnecessary complexity.

SAVE BEHAVIOR

- Disable or prevent duplicate submissions while saving.
- Show a subtle loading state.
- Show a clear success state.
- Surface validation/server errors cleanly.
- Do not silently lose unsaved changes.
- Refresh/revalidate the profile after saving.

SECURITY

All mutations must use the currently authenticated Supabase user.

Verify ownership server-side.

Do not trust a client-provided user ID.

Do not expose service-role credentials to the client.

Preserve RLS.

Do not weaken existing RLS policies just to make the feature work.

IMPORTANT:
If an existing RLS policy or query is insufficient, identify it and make the smallest secure change necessary.

API / SERVER ARCHITECTURE

Inspect the existing onboarding implementation and follow its established architecture.

Do not create a new API pattern just because it is convenient.

If the project uses route handlers, use route handlers.
If it uses server actions for a particular operation, follow that pattern where appropriate.

Keep server/client boundaries correct for Next.js 16.

ACCOUNT AUTH

Do NOT implement password creation/login in this task.

We will handle anonymous-account upgrade/password/account settings separately after profile editing.

DO NOT TOUCH

Do not implement:
- matches
- chat
- block/report UI
- password login
- phone OTP
- recommendation algorithms
- Three.js
- unrelated discover/swipe changes

However, if you discover a small existing bug that directly prevents the profile page from working, fix it minimally.

QUALITY BAR

Before finishing:
1. Run TypeScript/type checks.
2. Run lint if configured.
3. Verify the profile page loads for the current anonymous authenticated user.
4. Verify profile edits persist after refresh.
5. Verify photo upload/delete/reorder persist after refresh.
6. Verify another user's profile cannot be edited through the server/API.
7. Verify private fields (USN/email/auth ID) never appear in the public profile response.
8. Test mobile layout.
9. Check for console/runtime errors.
10. Check that existing onboarding and discover flows still work.

IMPORTANT IMPLEMENTATION RULE

Do not blindly start writing files.

First inspect the existing implementation and schema, then make the smallest coherent set of changes needed for Profile + Edit Profile.

At the end, report:
- files created
- files modified
- database changes, if any
- routes added
- server actions/API endpoints added
- validation added/reused
- security/RLS changes
- tests/checks performed
- any remaining limitations

Do not implement unrelated features.
