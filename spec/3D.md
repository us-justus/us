STEP 3D — INVITE LINKS / REFERRAL ATTRIBUTION

We are continuing the existing “us” campus-only dating app.

Current completed work:

- STEP 1 — pre-launch foundation + authoritative launch gating
- STEP 2 — username + permanent #spot
- STEP 3A — pre-launch home
- STEP 3B — username search + public profile
- STEP 3C — optional email/authentication

The next feature is:

STEP 3D — INVITE LINKS

IMPORTANT:
Implement ONLY invite links/referral attribution.

Do NOT implement:
- countdown
- Three.js / launch atmosphere
- image compression
- Discover changes
- Matches
- Chat
- Realtime
- notifications
- referral rewards
- referral leaderboard
- analytics platform
- post-launch features

Do not modify working Search, username, #spot, onboarding, or optional-email behavior except where invite attribution must naturally enter onboarding.

==================================================
PRODUCT GOAL
==================================================

A completed pre-launch user should be able to invite friends to join “us”.

Desired flow:

Existing user
    ↓
Pre-launch home
    ↓
invite friends
    ↓
personal invite link
    ↓
friend opens link
    ↓
invite landing/context
    ↓
enter the campus
    ↓
existing USN onboarding
    ↓
invite attribution preserved through onboarding
    ↓
new account completed

The invite system must NOT unlock:

Discover
Matches
Likes
Chat

Those remain controlled by the existing server-side launch gate.

==================================================
CORE IDENTITY RULE
==================================================

Invites MUST be associated internally with the stable auth user ID.

Do NOT use:

- username as the foreign key
- #spot as the foreign key
- USN as the invite identifier
- email as the invite identifier

Architecture:

auth.users.id
    ↓
invite
    ↓
invite token / code
    ↓
recipient attribution

Username and #spot are public product identities.

Invite attribution is a separate concept.

If a username changes in the future, existing invite links MUST remain valid.

#spot changes must never affect invite links.

Email changes must never affect invite links.

==================================================
STEP 2 — INVITE URL DESIGN
==================================================

Use an opaque invite token.

Preferred URL:

/invite/<token>

Do NOT use:

/@username
/username
/USN
/#spot
/auth/<id>

The token must not encode:

- USN
- email
- auth user ID in readable form
- private profile data

The token should be generated server-side using a cryptographically appropriate random mechanism.

Do not use Math.random().

Do not use sequential integers as public tokens.

Do not expose internal IDs in the URL.

==================================================
STEP 3 — DATABASE DESIGN
==================================================

Create the smallest appropriate schema.

A dedicated invite table is expected unless the audit finds an existing structure that genuinely fits.

Potential conceptual model:

invites
- id
- inviter_user_id
- token
- created_at
- maybe disabled_at / active state if actually needed

Do NOT add fields merely for future analytics.

Token uniqueness must be database-enforced.

inviter_user_id must reference the stable user identity.

Use appropriate indexes.

Do not store USN/email in invites.

Do not store the recipient's auth user ID until a recipient actually starts/finishes onboarding if the architecture needs that attribution.

If attribution needs to survive anonymous onboarding, design this carefully rather than creating a permanent recipient record prematurely.

==================================================
STEP 4 — RLS / SECURITY
==================================================

RLS must remain enabled.

Think carefully about the two operations:

A. Existing authenticated user creates/retrieves their invite.

B. Unauthenticated visitor resolves an invite token.

The invite token is intentionally public.

However:

Resolving a token must return ONLY the minimum public information needed by the invite landing page.

Never return:

- inviter auth ID
- inviter USN
- inviter email
- verification metadata
- private profile fields

If the invite landing page needs the inviter's username/#spot/nickname, expose only those explicitly public fields.

Do NOT make the entire invites table publicly readable.

Prefer a narrow server-side route/function for token resolution rather than broad SELECT access.

Do not introduce SECURITY DEFINER unless genuinely necessary.

If SECURITY DEFINER is necessary, explicitly justify it and lock down:
- search_path
- executable roles
- returned fields
- inputs

Never use service-role credentials in client code.

==================================================
STEP 5 — INVITE CREATION
==================================================

Completed users should have an “invite friends” action on the pre-launch home.

The server should:

1. authenticate the current user
2. ensure the user is a completed campus/permanent account
3. find or create their stable invite
4. return the public invite URL

Prefer one stable invite token per user rather than generating a new token every time they press Share.

This means:

same user
→ same invite URL

unless the invite is explicitly revoked in a future feature.

Do not generate a new database row on every share.

Creation must be concurrency-safe.

Two simultaneous requests must not create multiple active personal invite links.

Use database uniqueness / atomic behavior rather than a client-side check.

==================================================
STEP 6 — INVITE LANDING PAGE
==================================================

Create:

/invite/[token]

It should be server-rendered where practical.

States:

1. Valid invite
2. Invalid/nonexistent invite
3. Disabled invite, if disabled state exists
4. Self-invite
5. Already authenticated user

Keep the UI minimal and consistent with “us”.

Example conceptual copy:

“you've been invited.”

“join us.”

“just us.”

Then:

[ enter the campus ]

Do not copy exact wording blindly if it conflicts with existing product voice.

Use existing design tokens/components.

No heavy animation.

No Three.js.

No new UI library.

==================================================
STEP 7 — INVITE ATTRIBUTION
==================================================

This is important.

When a visitor opens:

/invite/<token>

the invite context must survive the transition into onboarding.

Do NOT require the visitor to manually type or copy the invite token.

Use the smallest safe mechanism compatible with the current architecture, such as a short-lived signed/opaque cookie or another server-controlled attribution mechanism.

Do NOT store sensitive identity data in the client.

The stored value should identify the invite token/context only.

Attribution should survive:

/invite/<token>
→ /
→ /onboarding
→ /onboarding/usn
→ /onboarding/email
→ /onboarding/password
→ /onboarding/profile
→ /onboarding/photos

It must also survive the optional-email path:

/onboarding/email
→ skip
→ password
→ profile
→ photos

Do not break the existing email/no-email onboarding state machine.

==================================================
STEP 8 — WHEN TO RECORD THE REFERRAL
==================================================

Do NOT permanently count a referral merely because someone opened a URL.

At minimum distinguish:

invite opened
from
account actually joined

For this first implementation, the important persisted event is:

completed onboarding user
    ↓
attributed to inviter

Do not build an analytics system.

Do not create a referral leaderboard.

Do not add rewards.

Do not overbuild event tracking.

The simplest acceptable model is:

new completed user
→ one inviter attribution

The attribution must be immutable after completion unless an explicit future product decision changes it.

==================================================
STEP 9 — SELF-INVITE / DUPLICATE HANDLING
==================================================

Handle these safely:

User opens their own invite:
- do not attribute themselves
- do not create self-referral

Existing completed user opens someone else's invite:
- do not modify their existing inviter attribution
- do not alter their account
- do not create duplicate onboarding state

Visitor opens invite and starts onboarding:
- preserve attribution

Visitor abandons onboarding:
- do not create a completed referral

Visitor resumes onboarding:
- attribution should remain available if technically feasible without introducing fragile state.

Do not create duplicate referral records for retries.

STEP 12 — LAUNCH STATE
==================================================

Invite links are a PRE-LAUNCH feature.

They must work regardless of:

launch_config.launched = false

or

launch_config.launched = true

The invite route itself must NOT be protected by the launch gate.

However:

Discover
Matches
Chat

must remain protected by the existing launch gate.

Do not accidentally make invite links a way to bypass launch restrictions.

==================================================
STEP 13 — PRIVACY
==================================================

Public invite resolution may expose ONLY intentionally public inviter information.

Never expose:

- USN
- email
- auth user ID
- verification records
- private profile metadata

Do not use SELECT *.

Use explicit projections.

Bound all token queries.

Do not expose database errors to users.

Invalid invite should produce a normal product-level invalid state, not raw Postgres/PostgREST output.

==================================================
STEP 14 — PERFORMANCE
==================================================

Invite resolution should be extremely cheap.

Requirements:

- indexed token lookup
- one bounded lookup
- no campus-wide query
- no polling
- no heavy dependencies
- no Three.js
- no duplicate auth requests
- no full profile fetch
- no image loading unless genuinely necessary

Invite generation should not repeatedly query the whole user profile.
