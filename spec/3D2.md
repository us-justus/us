==================================================
3. FINAL PHOTO PIPELINE
==================================================

The desired pipeline is:

user selects image
        ↓
client validates file
        ↓
crop editor
        ↓
user confirms crop
        ↓
preview
        ↓
resize / normalize
        ↓
high-quality encode
        ↓
processed Blob/File
        ↓
size/type validation
        ↓
Supabase Storage
        ↓
profile_photos row
        ↓
existing ordering/display

Do NOT upload the original image first and compress afterward.

The browser should process the image BEFORE upload.

==================================================
4. CROP UX
==================================================

Implement a lightweight crop editor.

Do NOT add a heavy image-editing library unless the audit proves it is genuinely necessary.

Prefer browser-native capabilities:

- image element / object URL
- Canvas where appropriate
- pointer/touch events
- native browser APIs

Avoid unnecessary dependencies.

The crop interaction must support:

MOBILE:
- touch drag
- pinch/zoom if practical
- smooth interaction
- no page scrolling while interacting with the crop area

DESKTOP:
- mouse drag
- wheel/pointer zoom if appropriate

The crop area should be visually obvious.

Use:

- darkened outside area
- clean crop frame
- subtle controls
- existing us design language

Do not create an Instagram-style editor.

No:
- filters
- stickers
- text
- beauty effects
- saturation controls
- arbitrary editing tools

Only framing/zoom.

==================================================
5. CROP ASPECT RATIO
==================================================

Before choosing the crop ratio, inspect the existing profile card/photo carousel and determine the intended display geometry.

Do NOT blindly choose 1:1.

The crop should match the actual profile-photo presentation as closely as practical.

If the existing card uses a portrait ratio, use that ratio.

If the current UI intentionally supports arbitrary photo ratios, preserve that behavior and use a consistent bounded crop only where needed.

Document the decision in the final report.

Do not change the Discover card layout as part of this task.

==================================================
6. IMAGE QUALITY
==================================================

The goal is:

VISUALLY LOSSLESS AT THE DISPLAY SIZE

NOT:

mathematically lossless.

Do not aggressively compress photos simply to hit a tiny file size.

Target:

- maximum longest edge around 1440px unless the audit shows a better existing display requirement
- high-quality JPEG encoding for photographic images
- sensible quality around 0.85–0.92
- preserve good detail
- avoid visible blocking/ringing
- avoid unnecessary upscaling

If the source is smaller than the target dimensions:

DO NOT upscale it unnecessarily.

For example:

800px image
→ keep approximately 800px

rather than:

800px
→ 1440px

The exact dimension/quality values should be validated against the existing UI rather than treated as sacred constants.

==================================================
7. IMAGE FORMAT
==================================================

Prefer a broadly compatible photographic format.

JPEG is acceptable/preferred for normal profile photographs.

Do NOT blindly convert every possible file format without checking browser support.

The agent must account for common user uploads such as:

- JPEG
- PNG
- WebP
- HEIC/HEIF where browser support is available

If the browser cannot decode/process a format reliably:

fail gracefully with a useful message rather than uploading a corrupted object.

Do not add a huge HEIC conversion dependency just for this MVP unless the audit shows it is required.

Do not pretend unsupported formats are supported.

==================================================
8. ORIENTATION
==================================================

This is important for phone photos.

Inspect how browser image decoding and Canvas rendering behave with EXIF orientation.

Ensure a portrait photo taken on a phone does not become sideways after processing.

Use browser-native orientation-aware APIs where available.

Do not manually implement every EXIF tag unless actually necessary.

Test at least:

- normal portrait
- landscape
- rotated phone photo

The processed image must visually match the user's original orientation.

==================================================
9. PREVIEW
==================================================

The user should see the cropped result before upload.

Flow:

SELECT
→ crop
→ DONE
→ preview
→ upload

The user must be able to cancel/re-edit before committing.

Do not upload while the user is still choosing the crop.

Existing photo slots/order behavior must remain intact.

==================================================
10. MULTIPLE PHOTOS
==================================================

Inspect the existing onboarding/profile editor behavior.

If multiple photos can be selected/uploaded:

process them individually.

Do NOT:

- upload all original files simultaneously
- create unbounded concurrent image processing
- freeze the UI

Use bounded/sequential processing where appropriate.

A user should always understand which image is being processed/uploaded.

Preserve existing maximum-photo constraints.

Do not increase or decrease the existing photo limit unless already specified elsewhere.

==================================================
11. UPLOAD UX
==================================================

During processing/upload:

show an intentional loading state.

Example conceptual states:

processing…
uploading…
done

Do not let users accidentally trigger duplicate uploads.

Disable the relevant action while processing.

Handle:

- processing failure
- upload failure
- network interruption
- storage failure

with a concise product-level message.

Do not show raw Supabase/PostgREST errors.

If upload fails:

the user must be able to retry without restarting onboarding/profile editing.

==================================================
12. SIZE VALIDATION
==================================================

The processed image should normally be substantially smaller than the original.

Do NOT enforce an unnecessarily tiny fixed size.

Use a reasonable safety ceiling for the processed upload.

If the processed file exceeds the ceiling:

- attempt a controlled quality reduction
- do not destroy visual quality unnecessarily
- if still too large, show a clear error

Do not simply reject a large original before processing if the browser can successfully reduce it.

The original source file may be large.

The processed output is what matters.

==================================================
13. OBJECT URL / MEMORY MANAGEMENT
==================================================

Be careful with browser memory.

For previews:

URL.createObjectURL()

must eventually be paired with:

URL.revokeObjectURL()

when the object is no longer needed.

Avoid retaining multiple large original blobs in React state unnecessarily.

Do not base64-encode huge images into React state.

Canvas/image processing should release temporary resources when possible.

This is especially important on mobile Safari.

==================================================
14. PERFORMANCE
==================================================

Image processing must not block the UI unnecessarily.

Do not add:

- WASM image processing frameworks
- large client libraries
- heavy editor packages

unless clearly justified.

Use:

- native Canvas
- Blob/File APIs
- object URLs
- requestAnimationFrame only where appropriate

Do not run image processing on page load.

Only process after the user selects a photo.

Do not process images that the user has not selected.

==================================================

==================================================

360px

- buttons ≥44px

- modal/sheet doesn't extend beyond viewport
- keyboard behavior doesn't break desktop usage

17. STORAGE CLEANUP
==================================================

Do not delete existing user photos during an upload failure.
