Implement persistent in-app notifications for `us` now. Keep the implementation focused and do not refactor unrelated code.

GOAL
----
When a user likes another user, the recipient gets a persistent in-app notification.

When the like is mutual, do NOT create a separate LIKE notification. Instead create a MATCH notification for both users with a direct action to continue the conversation.

Users can:
- read notifications
- delete notifications
- keep notifications in history until they explicitly delete them

Browser/OS push notifications are NOT part of this implementation yet, but the architecture must allow them later.

==================================================
1. DATABASE MIGRATION
==================================================

Create:

supabase/migrations/<timestamp>_notifications.sql

Create table:

notifications

Columns:

- id UUID PRIMARY KEY DEFAULT gen_random_uuid()
- user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE
    -- notification recipient
- actor_id UUID NULL REFERENCES auth.users(id) ON DELETE SET NULL
    -- user who caused the event
- type TEXT NOT NULL
- reference_id UUID NULL
    -- like.id or match.id
- read_at TIMESTAMPTZ NULL
- deleted_at TIMESTAMPTZ NULL
- created_at TIMESTAMPTZ NOT NULL DEFAULT now()

Allowed types initially:

- LIKE
- MATCH
- MESSAGE

MESSAGE is reserved for future use. Do not generate MESSAGE notifications yet.

Add indexes:

- notifications(user_id, created_at DESC)
- notifications(user_id, read_at, created_at DESC)

Notifications with deleted_at IS NOT NULL should not appear in normal notification queries.

==================================================
2. DUPLICATE PREVENTION
==================================================

Prevent duplicate notifications for the same user/type/reference.

Use an appropriate unique index such as:

UNIQUE(user_id, type, reference_id)

or an equivalent partial/index strategy if NULL reference IDs need special handling.

The like and match notification creation must be idempotent.

==================================================
3. RLS
==================================================

Enable RLS.

Authenticated users can:

SELECT only their own notifications.

UPDATE only their own notifications, and only fields needed for read/delete state.

Users must NOT be able to:

- insert arbitrary notifications
- create notifications for other users
- change actor_id
- change type
- change reference_id

Users can mark their own notifications as read.

Users can soft-delete their own notifications by setting:

deleted_at = now()

Do NOT physically delete notification rows from the client.

Notification creation happens server-side.

==================================================
4. LIKE → NOTIFICATION
==================================================

Find the existing like/swipe implementation.

Current behavior already works. Do not rewrite it.

When:

A likes B

check whether this action creates a mutual match.

CASE 1: NOT A MATCH

Create:

notifications:
- user_id = B
- actor_id = A
- type = LIKE
- reference_id = like.id

Notification copy:

"someone liked you"

If the existing profile system safely exposes the actor's username/name, the UI may show:

"[username] liked you"

Do not duplicate profile information into notifications.

CASE 2: MUTUAL LIKE

If A liking B causes a match:

DO NOT create the LIKE notification for B.

Instead create MATCH notifications:

For A:
- user_id = A
- actor_id = B
- type = MATCH
- reference_id = match.id

For B:
- user_id = B
- actor_id = A
- type = MATCH
- reference_id = match.id

Both notifications must be idempotent.

==================================================
5. MATCH NOTIFICATION UX
==================================================

Use the existing exact match copy:

"it's a match."
"you both liked each other."

Add a primary action:

"continue the conversation →"

Clicking that action should navigate directly to:

/chat/[matchId]

Use the actual existing match route/ID format.

Do not create a new chat system.

==================================================
6. NOTIFICATION API
==================================================

Create:

GET /api/notifications

Return:

{
  notifications,
  unread_count
}

Only return notifications belonging to the authenticated user.

Exclude:

deleted_at IS NOT NULL

Sort:

created_at DESC

Use a reasonable limit/pagination mechanism rather than returning unlimited history.

Create an endpoint/action for:

mark one notification read

Create another endpoint/action for:

delete one notification

Deletion means:

UPDATE notifications
SET deleted_at = now()

NOT physical deletion.

Optionally support "mark all as read" if it fits cleanly.

==================================================
7. NOTIFICATION UI
==================================================

Add a notification entry point to the authenticated navbar/app shell.

Use a simple notification/bell icon.

Show unread count:

🔔 2

Opening it should show persistent history.

Examples:

♡ someone liked you
   2 minutes ago

it's a match.
you both liked each other.
   yesterday

Each notification should have:

- read/unread visual state
- timestamp
- delete action

MATCH notification should have:

"continue the conversation →"

LIKE notification can link to the actor's profile if an existing profile route is available.

Do not invent a new profile route if one does not exist.

Keep the UI consistent with `us`:
minimal
romantic
clean
subtle
not a generic admin dashboard.

==================================================
8. READ BEHAVIOR
==================================================

Opening/seeing a notification should mark it read.

Read means:

read_at = current timestamp

Do NOT delete it.

A read notification remains visible in history until the user explicitly deletes it.

Unread count should be based on:

read_at IS NULL
AND deleted_at IS NULL

==================================================
9. DELETE BEHAVIOR
==================================================

Users can delete individual notifications.

Do:

deleted_at = now()

Do not remove the underlying like/match.

Deleting:

"someone liked you"

must NOT unlike the person.

Deleting:

"it's a match"

must NOT remove the match.

Notification deletion is purely notification-history management.

==================================================
10. REALTIME
==================================================

Use Supabase Realtime for new notifications if the project already uses Realtime.

Subscribe only to the current authenticated user's notifications.

When a new notification arrives:

- update notification list
- update unread count
- optionally show a subtle toast

The database remains the source of truth.

If the user is offline, notifications must still appear after reopening the app because they are persisted in the database.

==================================================
11. FUTURE PUSH SUPPORT
==================================================

Do NOT implement browser push now.

Do not couple notifications to browser sessions.

The notification table must remain the source of truth.

Later we should be able to add:

push_subscriptions

and deliver the same event through Web Push.

==================================================
12. IMPORTANT EXISTING ARCHITECTURE
==================================================

Do not modify:

- anonymous → permanent auth conversion
- password setup
- USN verification
- launch gating
- profiles
- swipe UI
- swipe animation
- existing likes/passes behavior

Prefer integrating notification creation at the existing server-side like/match boundary.

If the database trigger is currently responsible for creating matches, preserve that behavior and use the safest existing server/database boundary to create the corresponding MATCH notifications.

Avoid duplicate match creation.
