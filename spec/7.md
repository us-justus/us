The purpose is:

A verified/onboarded campus user should be able to find other public "us" users before launch using public identity information.

============================================================
PRODUCT REQUIREMENT
============================================================

Pre-launch users can:

1. open Search
2. search for another campus user
3. find them by username
4. optionally find them by public nickname if the existing product decision permits it
5. open a public profile
6. see only public profile information

Search does NOT unlock:

- Discover
- swiping
- likes
- passes
- matches
- chat

Search is a PRE-LAUNCH social discovery feature.

Search must explicitly select/project only fields that are intended to be public.

Never use SELECT * for search responses.

============================================================
PART 2 — SEARCHABLE FIELDS
============================================================

PRIMARY SEARCH FIELD:

username

Username is the canonical public lookup identity.

The existing username rules are:

- 3–30 characters
- A-Z / a-z
- 0-9
- underscore
- case-insensitive uniqueness
- public
- not a foreign key

Search should be case-insensitive.

Examples:

"atharva"
"ATHARVA"
"Atharva"

should all be able to find:

@Atharva

if it exists.

Do not alter the username normalization/uniqueness implementation from Step 2.

If nickname search is already explicitly approved:

- support it

If it is not explicitly approved:

- username-only search is the default for this slice
- do not silently introduce nickname search

If nickname search is implemented, it must remain secondary to username.

Never expose/search:

- USN
- email
- phone
- auth.users.id
- verification_records
- private identity metadata

============================================================
PART 4 — SEARCH QUERY
============================================================

Search must be server-backed.

Do NOT:
- download the campus user list
- filter in JavaScript
- fetch all profiles
- use unbounded SELECT queries
- perform client-side full-table search

The query must:

- normalize/trim input
- use the database
- be bounded
- have a hard result limit
- return only public fields
- be safe against SQL wildcard abuse
- be safe against injection
- support pagination if the chosen UX needs it

Initial result cap:

Use a small bounded limit such as 20.

Do not return hundreds/thousands of profiles.

============================================================
PART 5 — INDEXING
============================================================

Inspect the existing username index:

idx_profiles_username_lower

Use it where appropriate.

Do not create redundant indexes without justification.

If the chosen query pattern cannot use the current index efficiently, determine the smallest appropriate database index.

For username-prefix search, prefer an index/query pattern that can actually use PostgreSQL indexing.

Do not blindly add pg_trgm just because it is available.

Only add trigram/fuzzy search if the product requirement genuinely needs substring/fuzzy matching.

For this slice, username-first/prefix search is sufficient unless the existing SPEC.md says otherwise.

============================================================
PART 6 — SEARCH API
============================================================

Create the smallest appropriate server API.

Follow the existing project conventions.

For example, conceptually:

GET /api/search?q=...

Do not copy this exact route if the existing API organization suggests a better location.

Requirements:

- authenticated campus/pre-launch user only
- server-side product-state check
- do not allow anonymous public scraping
- bounded results
- public fields only
- no private fields
- do not accept arbitrary column names/order clauses
- no client-provided user IDs needed

If a signed-out user calls it:

→ reject.

If an incomplete onboarding user calls it:

→ reject.

If a completed pre-launch user calls it:

→ allow.

If launched:

→ search may remain available, provided that is consistent with the product model.

Do not unnecessarily restrict search to pre-launch if the feature is intended to survive launch.

Do this server-side using auth.uid() / existing server user identity.

Do NOT accept a user_id from the client to exclude.

============================================================
PART 12 — DEBOUNCING
============================================================

Search input should not fire a request for every keystroke.

Use a small debounce.

Avoid adding a dependency just for debounce.

Do not introduce polling.

Cancel/ignore stale requests where appropriate so:

request A for "ath"
request B for "atha"

cannot cause stale "ath" results to overwrite newer results.

Keep the implementation lightweight.

============================================================
PART 13 — MINIMUM QUERY LENGTH
============================================================

Do not hit the server for empty input.

Use a sensible minimum query length.

Because usernames are minimum 3 characters, a minimum of 2 or 3 is reasonable.

Prefer 2 or 3 based on the desired UX, but keep it consistent with the username rules.

Do not search the entire campus when the input is empty.
